### DTO、VO、POJO

#### DTO (Data Transfer Object)

**作用：在不同服务 / 接口 / 层之间传输数据**（比如前端→后端、服务 A→服务 B）。

核心场景

-   接收**前端传过来的参数**
-   微服务之间调用时传递数据
-   只包含**需要传输的字段**，不暴露敏感信息

```java
// 只接收前端传的账号和密码，不包含数据库字段
public class UserLoginDTO {
    private String username;
    private String password;
    // getter/setter
}
```



#### VO (View Object)

**作用：给前端页面展示数据**（Controller → 前端）。

核心场景

-   封装**返回给前端的最终数据**
-   可以组合多个表的数据
-   只保留页面需要的字段

```java
// 前端只需要展示这些，不需要密码、创建时间等
public class UserInfoVO {
    private Long userId;
    private String username;
    private String avatar;
    private Integer age;
    // getter/setter
}
```



#### POJO (Plain Old Java Object)

一种**统称、父概念**，不是具体的业务对象。

特点

-   只有**私有属性 + getter/setter**
-   无继承、无复杂逻辑
-   不依赖任何框架
-   **DTO、VO 本质上都是 POJO**

```java
// 标准POJO
public class User {
    private Long id;
    private String name;

    // getter、setter
    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
}
```

### 后端接收前端参数的格式

在苍穹外卖项目中，后端中的 Controller 需要接收来自前端的请求。

前端的常见 HTTP 请求为：

*   GET：查询、获取数据
*   POST：新增、提交数据
*   PUT：修改、更新数据
*   DELETE：删除数据

对应的三种传参方式：

*   路径参数
*   Query 参数
*   JSON 参数

对应这四种请求和三种传参方式，后端接收参数的方式概括为如下表格：

| 请求方式   | 主要用途 | 前端常用传参格式 | 后端接收注解             | 苍穹外卖常见场景 |
| ---------- | -------- | ---------------- | ------------------------ | ---------------- |
| **GET**    | 查询数据 | 路径 `/user/100` | **@PathVariable**        | 根据 ID 查询     |
|            |          | Query `?name=xx` | **省略 / @RequestParam** | 分页、条件查询   |
| **POST**   | 新增数据 | JSON             | **@RequestBody**         | 新增员工、登录   |
| **PUT**    | 修改数据 | JSON             | **@RequestBody**         | 修改员工、起停售 |
| **DELETE** | 删除数据 | 路径 `/user/100` | **@PathVariable**        | 根据 ID 删除     |

具体代码实现：

（1）路径参数

形式：

URL：`/admin/employee/100`

参数直接写在 URL 路径里面，用 `{}` 占位，接收注解为 `@PathVariable`

```java
@GetMapping("/admin/employee/{id}")
public Result getById(@PathVariable Long id)
```

（2）Query 参数

形式：

URL：`/admin/employee/page?name=张三&page=1&pagesize=10`

URL 后面用 `?` 开始，GET、POST 请求都能用，接收注解为 `@RequestParam`（可不写，默认就是）

```java
@GetMapping("/admin/employee/page")  // 如果已经在类注解中已经写明 @RequestMapping("/admin/employee")，可以省略重复的部分
public Result page(String name, Integer page, Integer pageSize)
```

当然，也可以将 `String name`、`Integer page`、`Integer pageSize` 这三项封装为一个DTO，然后直接用这个 DTO 来接收参数：

```java
@GetMapping("/admin/employee/page")
public Result page(EmployeePageQueryDTO employeePageQueryDTO)
```

其中 `EmployeePageQueryDTO` 的定义为：

```java
package com.sky.dto;

import lombok.Data;
import java.io.Serializable;

@Data
public class EmployeePageQueryDTO implements Serializable {
    // 员工姓名
    private String name;
    // 页码
    private int page;
    // 每页显示记录数
    private int pageSize;
}
```

（3）JSON 参数（请求体参数）

主要用于 POST、PUT 请求，用于传递复杂参数，接收注解为：`@RequestBody`

```java
@PostMapping("/admin/employee")
public Result save(@RequestBody EmployeeDTO employeeDTO)
```

### Spring Bean vs Java Bean

它们名字像，但不是一个概念。

JavaBean 是一种 Java 类的编码规范。
它强调的是“这个类长什么样”：

-   私有属性
-   无参构造
-   getter/setter
-   常用于承载数据

比如你项目里的：

-   `Orders`
-   `DishDTO`
-   `OrderVO`
-   `Result`

这些大多是 JavaBean 风格对象。

Spring Bean 是 Spring 容器管理的对象。
它强调的是“这个对象由谁管理”：

-   由 Spring 创建
-   由 Spring 注入依赖
-   由 Spring 管生命周期
-   可以享受 AOP、事务等 Spring 能力

比如你项目里的：

-   `OrderServiceImpl`
-   `DishController`
-   `AutoFillAspect`
-   `RedisConfiguration`
-   `JwtTokenUserInterceptor`

这些是 Spring Bean。

**一句话区分**
JavaBean 关注类的写法规范；Spring Bean 关注对象是否被 Spring 容器管理。

它们可以重叠，但不必然重叠：

-   一个 `Entity` 可能是 JavaBean，但通常不是 Spring Bean
-   一个 `OrderServiceImpl` 是 Spring Bean，但它不一定是典型的数据型 JavaBean
-   一个类可以既是 JavaBean 风格，又被 Spring 管理，但这不是必须的

你可以这样记：

“JavaBean 是 Java 对象的一种写法风格，Spring Bean 是 Spring 容器管理的对象。前者偏数据封装规范，后者偏框架生命周期和依赖管理。”



## 三层架构

在三层架构中，`Mapper` 就是 `Dao` 的现代实现形式，传统 `Dao` 接口在 MyBatis 持久层框架下，统一改名叫 `Mapper`，二者职责完全一致，只是叫法、编码形态不同，**三层架构本质没变**。

### Controller / Service / Dao

标准三层架构划分（**业务分层，职责解耦**），自上到下：

1.  **Controller 控制层（表现层）**

    接收前端请求、参数校验、调用 Service、封装返回结果、处理响应。

    对应苍穹外卖：`controller` 包下所有类。

2.  **Service 业务层**

    编写**核心业务逻辑**、事务控制、调用持久层、业务规则判断。

    对应苍穹外卖：`service / service.impl` 包。

3.  **Dao 持久层（数据访问层）**

    只负责**和数据库交互**：增删改查，不写业务逻辑。

    传统写法：`Dao 接口 + DaoImpl 实现类`。

>   调用链路：
>
>   **前端请求 → Controller → Service → Dao → MySQL**

### 传统 Dao 长什么样

在没有 MyBatis、MyBatis-Plus 之前，纯 JDBC / JdbcTemplate 时代，严格叫 **Dao**。

1、传统 Dao 接口

```java
public interface UserDao {
    User getUserById(Long id);
    int insertUser(User user);
}
```

2、Dao 实现类（DaoImpl）

里面写原生 JDBC 代码：获取连接、写 SQL、执行、封装结果、关闭连接。

```java
public class UserDaoImpl implements UserDao {
    @Override
    public User getUserById(Long id) {
        // 1. 获取数据库连接
        // 2. 编写 SQL
        // 3. 创建 Statement/PreparedStatement
        // 4. 执行查询、封装 User 对象
        // 5. 关闭资源
        return user;
    }
}
```

**痛点**：

-   大量重复代码（连接、关闭资源、参数设置）
-   SQL 和 Java 代码硬耦合，改 SQL 要改 Java 文件
-   开发效率极低

于是出现了**持久层框架 MyBatis**，并把 `Dao` 重新命名为 `Mapper`。

### Controller / Service / Mapper

#### 1、框架约定

MyBatis 官方统一将数据访问层接口命名为 Mapper，这是行业通用约定：

-   传统 JDBC $\to$ 叫 `Dao`
-   MyBatis / MyBatis-Plus $\to$ 统一叫 `Mapper`

`Mapper` = 新版 `Dao`，职责 100% 等价：只做数据库 CRUD。

#### 2、MyBatis 下 Mapper 的形态

MyBatis 只需要接口，不需要手写实现类，框架自动动态生成代理对象完成数据库操作。

（1）Mapper 接口（对应原来的 Dao 接口）

```java
// 苍穹外卖里典型的 Mapper
@Mapper
public interface UserMapper {
    // 方法名、参数、返回值 和 SQL 映射
    User getUserById(Long id);
    int insertUser(User user);
}
```

（2）XML / 注解 SQL（替代原来 DaoImpl 里的 JDBC 代码）

SQL 单独抽离到 `mapper/*.xml` 文件或注解中，解耦 Java 与 SQL。

调用链路完全没变：

>   Controller → Service → Mapper (原 Dao) → 数据库

#### 3、包名对比

| 分层       | 传统 JDBC 项目 | 苍穹外卖 (MyBatis)     | 职责               |
| ---------- | -------------- | ---------------------- | ------------------ |
| 控制层     | controller     | controller             | 接收请求、响应前端 |
| 业务层     | service        | service                | 业务逻辑、事务     |
| 持久层接口 | dao            | mapper                 | 定义数据库操作方法 |
| 持久层实现 | dao.impl       | 无（MyBatis 动态代理） | 框架自动实现       |

#### 4、三层架构 + Mapper 的完整执行流程

以「根据 ID 查询用户」为例：

1.  `Controller`：接收前端传的 `id`，调用 `userService.getUserById(id)`
2.  `Service`：接收参数，做业务判断，调用 `userMapper.selectById(id)`（可加事务）
3.  `Mapper`：MyBatis 找到对应 SQL，执行查询，返回数据
4.  数据原路返回：Mapper → Service → Controller → 前端

**原则始终不变**：

-   Controller 不碰数据库
-   Service 只写业务，不写 SQL







## Codex 总结

### 1. 基本类型 vs 包装类型

基本类型是 `int`、`long`、`double`、`boolean` 这种，特点是轻量、不是对象、不能为 `null`。
包装类是 `Integer`、`Long`、`Double`、`Boolean`，本质是对象，可以为 `null`。

为什么项目里更常用包装类？

-   数据库字段查出来后，可能为空，要允许 `null`
-   泛型只能放对象，不能放基本类型，比如 `List<Long>` 可以，`List<long>` 不行
-   很多框架参数绑定、JSON 转换、MyBatis 映射都更常和包装类打交道

:warning: 基本类型不是对象，包装类是对象。

:warning: 包装类可以为 `null`，所以更适合数据库和框架。

:warning: 泛型里只能放包装类，不能放基本类型。



### 2. 自动装箱和拆箱

自动装箱：long -> Long
自动拆箱：Long -> long

比如：

```java
Long userId = 1L;     // 自动装箱
long id = userId;     // 自动拆箱
```

这东西平时很方便，但有一个高频坑：
如果包装类是 null，拆箱时会空指针。

比如：

```java
Long userId = null; 
long id = userId; // NullPointerException
```

这和你的项目很相关。比如统计代码里：

```java
Integer totalOrderCount = orderMapper.countByMap(map);
```

如果你后面直接拿它当基本类型算，而且没判空，就容易出问题。

因此，应该需要“先判空再处理“。

:warning: 自动拆箱很方便，但 `null` 拆箱会空指针。



### 3. `String` 是什么，为什么这么常用

`String` 是不可变对象。
意思是：字符串一旦创建，内容不能改，所谓“修改”其实是新建了一个字符串。

项目里最常见的字符串用途：

-   token
-   订单号
-   地址拼接
-   Redis key
-   日志输出
-   报表里的日期串



### 4. `StringBuilder` 什么时候用

如果只是偶尔拼一次字符串，直接 `+` 可以。如果在循环里频繁拼接，优先 `StringBuilder`。

原因很简单：
`String` 不可变，每次 `+` 都可能创建新对象；循环里一直拼，会多创建很多中间字符串。

在 `OrderServiceImpl.java` 的 `getOrderDishesStr()` 里，你现在是先转成 `List<String>`，再 `String.join("", orderDishList)`。这也是一种减少手写拼接混乱的办法：

```java
    /**
     * 根据订单 id 获取菜品信息字符串
     */
    private String getOrderDishesStr(Orders orders) {
        // 查询订单菜品详情（订单中的菜品及其数量）
        List<OrderDetail> orderDetailList = orderDetailMapper.getByOrderId(orders.getId());

        // 将每一条订单菜品信息拼接为字符串（格式：宫保鸡丁*3;鱼香肉丝*2）
        List<String> orderDishList = orderDetailList.stream().map(x -> {
            String orderDish = x.getName() + "*" + x.getNumber() + ";";
            return orderDish;
        }).collect(Collectors.toList());

        // 将该订单对应的所有菜品信息拼接在一起
        return String.join("", orderDishList);
    }
```

如果以后手写循环拼菜品描述，`StringBuilder` 会更合适：

```java
    /**
     * 根据订单 id 获取菜品信息字符串
     */
    private String getOrderDishesStr(Orders orders) {
        // 查询订单菜品详情（订单中的菜品及其数量）
        List<OrderDetail> orderDetailList = orderDetailMapper.getByOrderId(orders.getId());

        StringBuilder sb = new StringBuilder();
        for (OrderDetail orderDetail : orderDetailList) {
            sb.append(orderDetail.getName()).append("*").append(orderDetail.getNumber()).append(";");
        }
        
        return sb.toString();
    }
```

:warning: 循环拼接字符串优先考虑 `StringBuilder`。



### 5.  什么是类，什么是对象

最简单理解：

-   `类` 是模板
-   `对象` 是根据模板创建出来的具体实例

比如你项目里的 `Orders.java`：

-   `Orders` 这个类，是“订单”这种数据结构的模板
-   `new Orders()` 创建出来的，才是某一个具体订单对象

你在 OrderServiceImpl.java 里经常写：

```
Orders orders = new Orders();
```

这就是“根据类创建对象”。

一句话记忆：
**类定义结构，对象承载数据。**



### 6. 为什么要封装

封装就是：
**不让外部直接乱碰属性，而是通过方法来访问和修改。**

Java 里最常见的方式是：

-   属性用 `private`
-   提供 `getter/setter`

比如：

```java
private Long id;
public Long getId() {
    return id;
}
public void setId(Long id) {
    this.id = id;
}
```

为什么这么做？

-   可以控制谁能改数据
-   可以在设置值时做校验
-   更符合面向对象设计

你项目里 `Entity`、`DTO`、`VO` 大多都是这种风格，所以本质上都是在遵守 Java 的封装习惯。

注意：
虽然很多时候 setter 看起来只是“赋值”，但它仍然是一层边界。以后如果要加校验，比 public 字段更容易扩展。



### 7.  构造方法是什么

构造方法是在创建对象时执行的方法，用来初始化对象。

最常见两种：

**无参构造**

```java
Orders orders = new Orders();
```

**有参构造**

```java
User user = new User(id, name);
```

为什么你项目里大量依赖无参构造？

-   `Spring`
-   `MyBatis`
-   `Jackson`
-   `BeanUtils`

这些框架经常需要先“new 一个空对象”，再把属性一个个塞进去。
所以很多数据对象都很适合保留无参构造。

一句话记忆：
**框架喜欢无参构造，因为它们要先创建对象，再做属性填充。**



### 8. 什么是 JavaBean

你项目里最常见的对象，其实大多都属于 JavaBean 风格。

通常满足这些特点：

-   有私有属性
-   有无参构造
-   有 getter/setter
-   用来承载数据

比如：

-   `Employee`
-   `Orders`
-   `DishDTO`
-   `OrderVO`

为什么 JavaBean 在后端项目里这么常见？

-   框架兼容性好
-   适合做参数绑定
-   适合做数据库映射
-   适合做 JSON 序列化和反序列化

所以你可以把 `Entity/DTO/VO` 理解成：
**不同职责的 JavaBean。**

职责区别再复习一遍：

-   `Entity`：更贴近数据库表
-   `DTO`：接收前端参数
-   `VO`：返回给前端的数据

>   如果一个类只有全参构造，**没有无参构造**，可能会对哪些框架场景造成不便？
>
>   答：**没有无参构造，会让很多依赖反射和属性填充的框架使用起来不顺手。**比如：
>
>   -   MyBatis 查询结果封装对象
>   -   Jackson 反序列化请求体
>   -   BeanUtils、反射工具创建对象
>   -   一些框架先实例化空对象再逐个填充属性的场景

>   你项目里很多地方用了 BeanUtils.copyProperties，它为什么更适合在 Entity/DTO/VO 这种结构相近的对象之间使用？
>
>   答：`BeanUtils.copyProperties` 适合在字段名和字段类型大体一致的 JavaBean 之间做快速拷贝，比如 `DTO -> Entity`、`Entity -> VO`。如果结构差异很大，或者需要复杂转换，它就不够合适了。

### 10. Java 异常大体怎么分

你现在先记最实用的一层：

-   Exception
-   RuntimeException

面试和项目里最常用的区分就是：

*   **checked exception**
    编译器强制你处理
    比如某些 IO、反射、外部调用异常

*   **unchecked exception**
    也就是运行时异常，继承 RuntimeException
    编译器不强制你处理

你项目里的业务异常，基本都属于第二类。比如：

-   `OrderBusinessException`
-   `DeletionNotAllowedException`
-   `LoginFailedException`

这些异常本质是：
**业务不满足条件，所以要中断流程并返回错误信息。**

>   -   业务异常：规则不满足，比如购物车为空、订单状态不对、超出配送范围
>   -   系统异常：程序或环境出了问题，比如数据库连不上、空指针、网络调用崩了



### 11. 为什么业务异常常继承运行时异常

这是后端项目里很高频的设计。

原因主要有 3 个：

1.  业务校验失败本来就是运行阶段才知道的
    比如“购物车是不是空”“订单状态对不对”，编译时不可能知道。
2.  不想在每一层都写很多 `throws` 和 `try-catch`
    如果业务异常都设计成受检异常，controller、service 一层层传会很重。
3.  更适合和 Spring 事务、全局异常处理配合
    抛出去后让统一异常处理器接住，代码更干净。

你项目里这个设计就很典型：

-   service 里发现业务不满足条件
-   直接 `throw new xxxBusinessException(...)`
-   最后由全局异常处理器统一转换成前端能看懂的错误结果



### 12. 你项目里的异常链路

### 16. 数组 vs `ArrayList`

-   长度固定

-   只能放对象，不能直接放基本类型

### 18. BeanUtils.copyProperties 到底在做什么

### 21. 什么是注解

你可以先把注解理解成：

**给类、方法、字段加上的一种“说明标签”。**

比如你项目里有很多注解：

-   `@RestController`
-   `@Service`
-   `@Autowired`
-   `@Transactional`
-   `@ApiOperation`
-   `@AutoFill`

它们本身不是业务逻辑，更多是在表达：

-   这个类是什么角色
-   这个方法有什么特征
-   这个字段要怎么处理

最关键的一点：
**注解本身不会自动完成复杂逻辑，真正干活的是读取注解的框架或代码。**

比如：

-   `@Service` 被 Spring 读取，然后注册成 Bean
-   `@Transactional` 被 Spring AOP 读取，然后织入事务逻辑
-   `@AutoFill` 被你的 AutoFillAspect 读取，然后执行自动填充



1.  注解本质上是一种标记。
2.  注解本身不干活，真正干活的是读取注解的代码。
3.  反射可以在运行时获取类、方法、注解并执行方法。
4.  `@AutoFill` 是你项目里的自定义注解，用来标记公共字段自动填充。
5.  反射适合做通用能力，但不适合在普通业务里到处滥用。



“`@AutoFill` 适合放在切面里，因为它是典型的横切逻辑，统一处理能减少重复代码并保证规则一致。切面里通过反射去查找 setter 并执行，这种方式很灵活，但如果方法名写错，通常要到运行时才会暴露问题。这也说明反射更适合封装框架层或通用能力，而不适合在普通业务代码里到处使用。”

### 23. 什么是反射

最简单的理解：

**反射就是程序在运行时去查看和操作类的信息。**

平时你是“提前知道类长什么样”。

-   拿到注解里的值
-   再拿到参数对象
-   再通过方法名去调用它的 setter

这就是非常典型的反射使用。

### 26. 为什么需要 AOP

你项目里有一类逻辑，很典型：

-   不是核心业务本身
-   但很多地方都要做
-   而且规则基本一致

比如：

-   自动填充公共字段
-   日志
-   事务
-   权限校验

如果每个地方都手写，会有几个问题：

-   重复代码多
-   容易漏
-   规则不统一
-   后期改起来很麻烦

所以 AOP 的核心意义就是：

**把这种“横着切很多地方”的公共逻辑抽出来统一处理。**



### 27. 什么是 AOP

最简单理解：

-   OOP 更关注“把功能按对象分开”
-   AOP 更关注“把公共逻辑横向抽出来”

你现在先别记太抽象，直接记一句：

**AOP = 在目标方法执行前后，统一加一层处理。**

比如：

-   方法执行前自动填充字段
-   方法执行前做权限检查
-   方法执行后打日志



### 28. AOP 里最重要的 3 个概念

#### 1. 切点

**拦哪些方法**

比如你项目里：

```java
@Pointcut("execution(* com.sky.mapper.*.*(..)) && @annotation(com.sky.annotation.AutoFill)")
```

意思就是：

-   拦截 `com.sky.mapper` 包下的方法
-   而且要求方法上有 `@AutoFill`

这就是在定义“哪些地方需要增强”。

#### 2. 通知

**在什么时候做增强**

常见有：

-   `@Before`：方法执行前
-   `@After`：方法执行后
-   `@Around`：方法前后都能管

你项目里用的是：

```java
@Before("autoFillPointCut()")
```

意思就是：
**在目标 mapper 方法执行前，先做自动填充。**

#### 3. 切面

**切点 + 通知 + 具体逻辑，合起来就是切面**

你项目里的：

-   `AutoFillAspect.java`

就是一个切面类。

它里面包含：

-   切点定义
-   前置通知
-   真正的自动填充逻辑



### 29. 用你的项目把 AutoFillAspect 串起来

你现在把它理解成这 4 步：

#### 第一步：先标记

在 mapper 方法上加：

```java
@AutoFill(OperationType.INSERT)
```

或者：

```java
@AutoFill(OperationType.UPDATE)
```

意思是：

-   这个方法执行时，需要自动填充
-   而且要知道是插入还是更新

#### 第二步：切面找到它

`AutoFillAspect` 通过切点表达式找到这些方法。

也就是说，AOP 在做：
**“看到这个注解的方法，我就要插手一下。”**

#### 第三步：方法执行前先增强

`@Before` 通知会在 mapper 方法真正执行前先跑一遍。

这里做的事情包括：

-   读取注解
-   取出操作类型
-   取出实体对象
-   通过反射设置公共字段

#### 第四步：目标方法再执行

当字段补好了，真正的 mapper 插入/更新方法才继续执行。

所以这整条链路就是：

**mapper 方法打标记 -> AOP 拦截 -> 自动填充字段 -> 执行 SQL**



### 30. AOP 和拦截器有什么区别

这题很容易被追问，你现在先记一个够用版本：

#### 拦截器

更偏 Web 层
主要拦 HTTP 请求

比如你项目里的：

-   `JwtTokenAdminInterceptor`
-   `JwtTokenUserInterceptor`

它们处理的是：

-   请求有没有 token
-   token 合不合法
-   当前用户是谁

#### AOP

更偏方法层
主要拦某些 Bean 的方法执行

比如你项目里的：

-   `AutoFillAspect`

它处理的是：

-   mapper 方法执行前，要不要补字段

一句话区分：
**拦截器拦请求，AOP 拦方法。**



“`AutoFillAspect` 是一个典型 AOP 场景。公共字段自动填充不是某个具体业务，而是多个模块都会用到的横切逻辑。项目通过 `@Pointcut` 找到 mapper 包下带 `@AutoFill` 的方法，再通过 `@Before` 在 SQL 执行前统一填充字段。拦截器主要拦 HTTP 请求，AOP 主要拦方法执行。”

> :question: Spring 的事务管理是 AOP 吗？
>
>答：是的，Spring 的 @Transactional 可以理解为典型的 AOP 应用。它在业务方法执行前开启事务，方法正常结束后提交事务，如果出现符合回滚规则的异常就回滚。开发者只需要在方法上声明注解，事务的开启、提交、回滚由 Spring 通过代理和 AOP 机制完成。**事务也是公共能力，适合通过 AOP 在方法前后统一增强。**



### 31. ThreadLocal

`ThreadLocal` 适合保存“当前线程独有的上下文数据”。

```java
package com.sky.context;

public class BaseContext {

    public static ThreadLocal<Long> threadLocal = new ThreadLocal<>();

    public static void setCurrentId(Long id) {
        threadLocal.set(id);
    }

    public static Long getCurrentId() {
        return threadLocal.get();
    }

    public static void removeCurrentId() {
        threadLocal.remove();
    }

}
```

`ThreadLocal` 很好用，但不是没有风险。

最大风险是：**线程复用时，如果不清理，旧数据可能残留。**

Web 服务器通常用线程池。
请求结束后，线程不会销毁，而是回到线程池继续处理下一个请求。

如果你之前在线程里存过用户 id，但请求结束没有 `remove()`，理论上后续请求可能拿到旧数据。

所以更规范的做法是：

```java
BaseContext.removeCurrentId();
```

一般会放在请求结束后清理，比如拦截器的 `afterCompletion` 里。

你项目里已经有 `removeCurrentId()` 方法，但当前拦截器里主要做了 `set`，这就是一个可以在面试里主动说的优化点。



“项目里 JWT 拦截器解析 token 后，将当前用户 id 存入 `BaseContext`，底层是 `ThreadLocal`。这样同一个请求线程里的 service 和 AOP 都能拿到当前用户 id，同时不同请求之间不会互相覆盖。相比层层传参，`ThreadLocal` 能减少方法签名污染，但在线程池环境下用完要及时 `remove`，避免上下文残留。”



“当前项目已经封装了 `BaseContext.removeCurrentId()`，但拦截器里只做了 `set`，没有在请求完成后清理。后续可以在 `HandlerInterceptor` 的 `afterCompletion` 方法里调用 `BaseContext.removeCurrentId()`，这样每个请求结束后都清掉当前线程的用户上下文，避免线程池复用时残留旧用户 id。”

```java
@Override
public void afterCompletion(HttpServletRequest request,
                            HttpServletResponse response,
                            Object handler,
                            Exception ex) {
    BaseContext.removeCurrentId();
}
```



### 32. **Stream 是什么**

Stream 不是集合本身，它是集合的一种处理方式。

比如：

```java
orderDetailList.stream()
```

意思是：
**把这个 List 变成一条可以连续处理的数据流。**

然后你可以接：

-   `map`：转换
-   `filter`：筛选
-   `collect`：收集成集合
-   `reduce`：归约汇总

注意：
Stream 不会神奇地改变原集合，它通常是基于原集合生成一个新的结果。



#### map 是转换

map 的核心意思是：
**把一种对象转换成另一种对象。**

你项目里最典型的是 OrderServiceImpl.java 的“再来一单”：

```java
List<ShoppingCart> shoppingCartList = orderDetailList.stream().map(x -> {
    ShoppingCart shoppingCart = new ShoppingCart();
    BeanUtils.copyProperties(x, shoppingCart, "id");
    shoppingCart.setUserId(userId);
    shoppingCart.setCreateTime(LocalDateTime.now());
    return shoppingCart;
}).collect(Collectors.toList());
```

这段的意思就是：

把每个 `OrderDetail` 转成一个 `ShoppingCart`，最后收集成 `List<ShoppingCart>`。

所以 `map` 你就记成一个词：转换。



#### collect 是收集结果

Stream 处理完后，要把结果拿回来。
最常见就是：

```java
.collect(Collectors.toList())
```

意思是：
把处理后的结果重新收集成 List。

比如上面：

-   原来是 `List<OrderDetail>`
-   map 后变成很多个 `ShoppingCart`
-   collect 后得到 `List<ShoppingCart>`



#### filter 是筛选

你项目里 `filter` 用得不算多，但它很常见。

比如：

```java
List<Orders> completedOrders = ordersList.stream()
    .filter(order -> order.getStatus().equals(Orders.COMPLETED))
    .collect(Collectors.toList());
```

意思是：
只保留已完成订单。



#### reduce 是归约汇总

`reduce` 适合把一批数据汇总成一个值。

你项目里在 `ReportServiceImpl.java` 有类似逻辑：

```java
Integer totalOrderCount = orderCountList.stream().reduce(Integer::sum).get();
```

意思是：
把列表里的订单数加起来。

:warning: ​但这里有个小风险：
如果列表为空，`reduce(Integer::sum)` 返回的事一个空的 `Optional`，再调用 `.get()` 会抛出 `NoSuchElementException` 异常。

更稳一点可以写：

```java
Integer totalOrderCount = orderCountList.stream().reduce(0, Integer::sum);
```

这表示从 0 开始累加，不怕空列表。

这个点面试里能说出来，是加分项。



#### Stream 什么时候适合用

-   代码能变得更清晰时

比如：

-   一写出来比 for 循环更难读

### 33. **什么是事务**

事务就是把多个数据库操作看成一个整体。

比如用户下单不是一条 SQL：

1.  插入订单主表
2.  批量插入订单明细
3.  清空购物车

这三步必须整体成功。
如果订单主表插入成功，但明细插入失败，就会出现脏数据。
所以要用事务保证：

**要么三步都成功，要么一起回滚。**



事务有四个特性，叫 ACID。

#### A：原子性

一组操作要么都成功，要么都失败。

比如下单三步不能只成功一半。

#### C：一致性

事务前后，数据要从一个正确状态变到另一个正确状态。

比如不能出现“有订单但没有订单明细”的异常状态。

#### I：隔离性

多个事务并发执行时，彼此不能随便互相干扰。

比如两个人同时操作订单，不能把状态改乱。

#### D：持久性

事务提交后，数据要真正保存下来。

比如订单提交成功后，数据库里应该能查到。

你现在先不用背复杂理论，先能结合项目举例就够了。



### 34. **项目里哪些地方需要事务**

你项目里很典型：

-   `OrderServiceImpl.java` 的 `submitOrder`
-   `DishServiceImpl.java` 的新增、删除
-   `SetmealServiceImpl.java` 的新增、删除、修改

它们共同特点是：

**一个业务动作里包含多次数据库写操作。**

这种就很适合加 `@Transactional`。



### 35. **`@Transactional` 做了什么**

`@Transactional` 是 Spring 声明式事务注解。

你加在 `service` 方法上后，Spring 会在方法执行时帮你做：

1.  方法开始前开启事务
2.  方法正常执行完提交事务
3.  方法执行中出现符合规则的异常就回滚事务

这背后也是 AOP 思想：
**在业务方法前后加事务控制。**



### 36. **什么异常会触发回滚**

默认情况下，Spring 对运行时异常 `RuntimeException` 和 `Error` 回滚。

你项目里的业务异常很多继承运行时异常，所以抛出后可以触发回滚。

比如：

-   `ShoppingCartBusinessException`
-   `OrderBusinessException`
-   `DeletionNotAllowedException`

注意：
如果是受检异常 `Exception`，默认不一定回滚，除非配置：

```java
@Transactional(rollbackFor = Exception.class)
```

你项目里有些方法声明了 `throws Exception`，但是否回滚要看异常类型和事务配置。这个作为进阶点先记住。



#### 事务失效的常见情况

4 个高频点。

1. 方法不是 Spring Bean 调用的：如果对象是自己 `new` 出来的，不归 Spring 管，事务不生效。

2. 同类内部方法调用：比如同一个类里 `methodA()` 调 `methodB()`，而事务只加在 `methodB()` 上，可能绕过 Spring 代理，导致事务不生效。

3. 异常被 catch 了没抛出去：如果异常被你自己吃掉，Spring 以为方法正常结束，就会提交。

4. 默认只回滚运行时异常：受检异常默认不一定回滚，需要 `rollbackFor = Exception.class`。



### 37. **为什么事务通常放在 service 层**

因为 service 层负责完整业务编排。

比如下单：

-   校验地址簿
-   查购物车
-   插订单
-   插明细
-   清购物车
-   返回结果

mapper 只知道单个数据库操作，不知道完整业务。
controller 又不应该负责业务细节。

所以事务边界放在 service 层最自然。

一句话记忆：
**事务应该包住一个完整业务动作，而 service 层正好承载业务动作。**

### 39. **动态 SQL 是什么**

动态 SQL 就是根据条件拼接不同 SQL 片段。

比如分页查询订单时，有些条件可能有，有些没有：

-   订单号
-   手机号
-   状态
-   下单时间
-   用户 id

如果每种组合都写一条 SQL，会爆炸。

所以 MyBatis 提供动态 SQL 标签：

-   `<if>`
-   `<where>`
-   `<foreach>`
-   `<set>`

比如：

```xml
<where>
    <if test="status != null">
        and status = #{status}
    </if>
    <if test="number != null">
        and number like concat('%', #{number}, '%')
    </if>
</where>
```

意思是：
**哪个条件有值，就拼哪个条件。**



### 40. **PageHelper 分页是怎么用的**

你项目里分页常见写法是：

```java

```

它的思路是：

1.  在查询前调用 `PageHelper.startPage(...)`
2.  PageHelper 拦截后面的 SQL
3.  自动加上分页逻辑
4.  返回分页结果，包括总数和当前页数据

所以注意顺序：

**必须先 `startPage`，再执行查询。**

如果顺序反了，就不会对那条查询生效。

### 46. **为什么普通 HashMap 有并发风险**

普通 `HashMap` 不是线程安全的。

如果多个线程同时：

-   `put`
-   `remove`
-   遍历
-   发送消息时读取

可能出现：

-   数据覆盖
-   数据不一致
-   遍历时被修改导致异常
-   某些连接丢失或状态错乱

在 WebSocket 场景下，多个客户端可能同时建立连接、断开连接、接收消息。
这些事件不一定只由一个线程串行处理。

所以 `HashMap` 并发访问是不稳的。



### 47. `ConcurrentHashMap` 是什么

`ConcurrentHashMap` 是 Java 提供的并发安全 Map。

它适合多个线程同时读写。
相比直接给整个 Map 加大锁，它通常并发性能更好。

你的项目里可以把：

```java
private static Map<String, Session> sessionMap = new HashMap<>();
```

优化为：

```java
private static final Map<String, Session> sessionMap = new ConcurrentHashMap<>();
```

这就是一个很自然的项目优化点。

面试里可以这样说：

“当前教学项目中 WebSocket 会话使用普通 `HashMap` 保存，功能测试没问题。但真实并发环境下多个连接可能同时 `put/remove/send`，普通 `HashMap` 不是线程安全的，可以改成 `ConcurrentHashMap`。”



### 48. **Spring Bean 默认是单例，也要注意成员变量**

这是很多人容易忽略的点。

Spring 里的 `@Service`、`@Controller` 默认是单例。
也就是说，同一个 Bean 对象会被多个请求线程共享。

所以在单例 Bean 里，不要随便放“会被请求修改的成员变量”。

比如这样就危险：

```java
@Service public class OrderServiceImpl {
    private Long currentUserId;
}
```

如果多个请求同时改这个字段，用户 id 就可能串。

你项目里用 `ThreadLocal` 保存当前用户 id，而不是把它放到 service 成员变量里，这就是正确方向。

### 50. 垃圾回收 GC 是什么

Java 不需要你手动 `free/delete` 对象。
JVM 会自动回收不再使用的对象。

所谓“不再使用”，最常见理解是：

**没有任何可达引用指向它。**

比如一个请求里创建了很多：

-   `Orders`
-   `OrderVO`
-   `List<OrderDetail>`
-   `HashMap`

请求结束后，如果这些对象没有被其他地方引用，它们就可以被 GC 回收。



### 51. 为什么还要关心对象数量

虽然 Java 有 GC，但不代表可以随便创建对象。

如果短时间创建大量对象：

-   堆内存压力变大
-   GC 更频繁
-   接口响应可能抖动
-   极端情况会 OOM

比如报表导出、批量查询、大量集合转换，都可能创建很多对象。

你项目里的 POI 导出 Excel 就是一个需要注意内存的场景。
真实大数据量导出时，不能无脑一次性把所有数据都堆在内存里。



### 52. 类加载是什么

类加载就是 JVM 把 `.class` 文件加载进内存，变成可以使用的类信息。

比如项目启动时，Spring 会扫描很多类：

-   controller
-   service
-   mapper
-   configuration
-   aspect

JVM 需要先加载这些类，Spring 才能创建 Bean。

你现在先记一句：

### 56. **支付和订单幂等**

幂等的意思是：

**同一个操作执行多次，结果应该和执行一次一样。**

支付回调尤其需要幂等。
因为支付平台可能重复通知。

如果同一个支付成功通知来了两次，系统不能：

-   重复改状态导致异常
-   重复推送多次来单消息
-   重复发放优惠
-   重复创建数据

所以真实支付回调一般会：

-   根据订单号查订单
-   判断当前支付状态
-   如果已经支付过，直接返回成功
-   没支付过才更新状态

你项目里支付逻辑偏教学实现，后续可以把“支付幂等”作为优化点。

### 62. **面试官深挖时怎么回答**

#### 问：你项目里为什么用 ThreadLocal？

答：
“因为 JWT 拦截器解析出用户 id 后，后续 service、AOP 都可能需要使用。如果层层传参，会污染很多方法签名。`ThreadLocal` 可以保存当前请求线程的上下文数据，不同线程之间互不影响。不过线程池复用时要注意请求结束后清理。”

#### 问：AOP 自动填充怎么实现？

答：
“先在 mapper 方法上加自定义 `@AutoFill` 注解，标记插入或更新操作。切面通过切点拦截 mapper 包下带注解的方法，在方法执行前读取注解值、获取实体参数，再通过反射调用 setter 填充时间和当前用户 id。”

#### 问：Redis 缓存怎么做？

答：
“用户端查询菜品时先按分类 id 拼 key 查 Redis，命中直接返回；未命中再查数据库并写入 Redis。管理端新增、修改、删除、启停售菜品后删除相关缓存，避免用户端读取旧数据。”

#### 问：WebSocket 用来做什么？

答：
“支付成功后，后端会更新订单状态，并通过 WebSocket 给商家端推送来单提醒。用户催单时也会通过 WebSocket 推送消息。相比 HTTP 轮询，WebSocket 更适合服务端主动推送。”



### 63. **你最终可以这样完整讲项目**

“我做的是苍穹外卖后端项目，分管理端和用户端。管理端包括员工、分类、菜品、套餐、订单、报表等功能，用户端包括微信登录、菜品套餐浏览、购物车、地址簿、下单和支付。项目基于 Spring Boot、MyBatis、Redis 开发，采用 Maven 多模块和 controller、service、mapper 分层结构。

我比较重点负责和理解的是订单链路。用户下单时，请求先经过 JWT 拦截器，解析 token 后把用户 id 放入 `BaseContext`，后续业务层通过它获取当前用户。下单时会校验地址簿、购物车和配送范围，然后在事务中写订单主表、订单明细表，并清空购物车，保证多表数据一致。支付成功后会更新订单状态，并通过 WebSocket 推送来单提醒，超时未支付订单则由定时任务兜底取消。

项目里还做了一些公共能力，比如通过自定义 `@AutoFill` 注解和 AOP，在 mapper 执行前统一填充创建时间、修改时间、操作人，减少重复代码。用户端菜品和套餐这种读多写少的数据使用 Redis 缓存，管理端修改数据后清理缓存，避免读到旧数据。

如果继续优化，我会补充` ThreadLocal` 请求结束清理、WebSocket 会话并发安全、支付回调幂等、缓存过期和穿透击穿处理，以及核心业务的自动化测试。”
