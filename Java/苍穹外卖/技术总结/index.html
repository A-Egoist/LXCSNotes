    技术总结¶

    项目结构¶

    该项目是一个前后端分离的项目，前端项目由管理端（Web）和用户端（小程序）组成，后端服务用 Java 实现。

    管理端（Web）基于 nginx 运行，用户端（小程序）使用微信小程序实现。

    后端工程基于 maven 进行项目构建，并且进行分模块开发。

    DTO、VO、POJO¶

    DTO (Data Transfer Object)¶

    作用：在不同服务 / 接口 / 层之间传输数据（比如前端→后端、服务 A→服务 B）。

    核心场景

    • 接收前端传过来的参数
    • 微服务之间调用时传递数据
    • 只包含需要传输的字段，不暴露敏感信息
    1
2
3
4
5
6
    // 只接收前端传的账号和密码，不包含数据库字段
public class UserLoginDTO {
    private String username;
    private String password;
    // getter/setter
}

    VO (View Object)¶

    作用：给前端页面展示数据（Controller → 前端）。

    核心场景

    • 封装返回给前端的最终数据
    • 可以组合多个表的数据
    • 只保留页面需要的字段
    1
2
3
4
5
6
7
8
    // 前端只需要展示这些，不需要密码、创建时间等
public class UserInfoVO {
    private Long userId;
    private String username;
    private String avatar;
    private Integer age;
    // getter/setter
}

    POJO (Plain Old Java Object)¶

    一种统称、父概念，不是具体的业务对象。

    特点

    • 只有私有属性 + getter/setter
    • 无继承、无复杂逻辑
    • 不依赖任何框架
    • DTO、VO 本质上都是 POJO

    public void setId(Long id) { this.id = id; }
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }

    RESTful API 风格¶

    RESTful API 风格，行业统一标准：

    • GET：查询（查数据）
    • POST：新增（增数据）
    • PUT：修改（改数据）
    • DELETE：删除（删数据）
    前端 HTTP 请求类型 后端 Controller 必须写的注解
    GET @GetMapping
    POST @PostMapping
    PUT @PutMapping
    DELETE @DeleteMapping

    使用 Swagger 生成接口文档¶

    Swagger 是一个规范和完整的框架，用于生成、描述、调用和可视化 RESTful 风格的 Web 服务(https://swagger.io/)。 它的主要作用是：

    1. 使得前后端分离开发更加方便，有利于团队协作

    2. 接口的文档在线自动生成，降低后端开发人员编写接口文档的负担

    3. 功能测试

    后端接收前端参数的格式¶

    在苍穹外卖项目中，后端中的 Controller 需要接收来自前端的请求。

    前端的常见 HTTP 请求为：

    • GET：查询、获取数据
    • POST：新增、提交数据
    • PUT：修改、更新数据
    • DELETE：删除数据

    对应的三种传参方式：

    • 路径参数
    • Query 参数
    • JSON 参数

    Query ?name=xx 省略 / @RequestParam 分页、条件查询

    Spring IOC¶

    IOC 是 Inversion of Control，控制反转。对象创建的控制权，从程序员手里，交给 Spring 容器。

    DI 是 Dependency Injection，依赖注入。

    它是 IOC 的具体实现方式。

    IOC 是容器管对象，DI 是容器把对象注入给需要它的地方。

    Spring Bean vs Java Bean¶

    它们名字像，但不是一个概念。

    JavaBean 是一种 Java 类的编码规范。 它强调的是“这个类长什么样”：

    • 私有属性
    • 无参构造
    • getter/setter
    • 常用于承载数据

    比如你项目里的：

    • Orders
    • DishDTO
    • OrderVO
    • Result

    这些大多是 JavaBean 风格对象。

    Spring Bean 是 Spring 容器管理的对象。 它强调的是“这个对象由谁管理”：

    • 由 Spring 创建
    • 由 Spring 注入依赖
    • 由 Spring 管生命周期
    • 可以享受 AOP、事务等 Spring 能力

    比如你项目里的：

    • OrderServiceImpl
    • DishController
    • AutoFillAspect
    • RedisConfiguration
    • JwtTokenUserInterceptor

    这些是 Spring Bean。

    一句话区分 JavaBean 关注类的写法规范；Spring Bean 关注对象是否被 Spring 容器管理。

    它们可以重叠，但不必然重叠：

    • 一个 Entity 可能是 JavaBean，但通常不是 Spring Bean
    • 一个 OrderServiceImpl 是 Spring Bean，但它不一定是典型的数据型 JavaBean
    • 一个类可以既是 JavaBean 风格，又被 Spring 管理，但这不是必须的

    你可以这样记：

    “JavaBean 是 Java 对象的一种写法风格，Spring Bean 是 Spring 容器管理的对象。前者偏数据封装规范，后者偏框架生命周期和依赖管理。”

    三层架构¶

    在三层架构中，Mapper 就是 Dao 的现代实现形式，传统 Dao 接口在 MyBatis 持久层框架下，统一改名叫 Mapper，二者职责完全一致，只是叫法、编码形态不同，三层架构本质没变。

    Controller / Service / Dao¶

    标准三层架构划分（业务分层，职责解耦），自上到下：

    1. Controller 控制层（表现层）

      接收前端请求、参数校验、调用 Service、封装返回结果、处理响应。

      对应苍穹外卖：controller 包下所有类。

    2. Service 业务层

      编写核心业务逻辑、事务控制、调用持久层、业务规则判断。

      对应苍穹外卖：service / service.impl 包。

    3. Dao 持久层（数据访问层）

      只负责和数据库交互：增删改查，不写业务逻辑。

      传统写法：Dao 接口 + DaoImpl 实现类。

    调用链路：

    前端请求 → Controller → Service → Dao → MySQL

    Controller / Service / Mapper¶

    1、框架约定¶

    MyBatis 官方统一将数据访问层接口命名为 Mapper，这是行业通用约定：

    • 传统 JDBC \(\to\) 叫 Dao
    • MyBatis / MyBatis-Plus \(\to\) 统一叫 Mapper

    Mapper = 新版 Dao，职责 100% 等价：只做数据库 CRUD。

    2、MyBatis 下 Mapper 的形态¶

    MyBatis 只需要接口，不需要手写实现类，框架自动动态生成代理对象完成数据库操作。

    （1）Mapper 接口（对应原来的 Dao 接口）

    （2）XML / 注解 SQL（替代原来 DaoImpl 里的 JDBC 代码）

    SQL 单独抽离到 mapper/*.xml 文件或注解中，解耦 Java 与 SQL。

    调用链路完全没变：

    Controller → Service → Mapper (原 Dao) → 数据库

    3、包名对比¶

    分层 传统 JDBC 项目 苍穹外卖 (MyBatis) 职责
    控制层 controller controller 接收请求、响应前端
    业务层 service service 业务逻辑、事务
    持久层接口 dao mapper 定义数据库操作方法
    持久层实现 dao.impl 无（MyBatis 动态代理） 框架自动实现

    4、三层架构 + Mapper 的完整执行流程¶

    以「根据 ID 查询用户」为例：

    1. Controller：接收前端传的 id，调用 userService.getUserById(id)
    2. Service：接收参数，做业务判断，调用 userMapper.selectById(id)（可加事务）
    3. Mapper：MyBatis 找到对应 SQL，执行查询，返回数据
    4. 数据原路返回：Mapper → Service → Controller → 前端

    原则始终不变：

    • Controller 不碰数据库
    • Service 只写业务，不写 SQL

    Codex 总结¶

    1. 基本类型 vs 包装类型¶

    基本类型是 int、long、double、boolean 这种，特点是轻量、不是对象、不能为 null。 包装类是 Integer、Long、Double、Boolean，本质是对象，可以为 null。

    为什么项目里更常用包装类？

    • 数据库字段查出来后，可能为空，要允许 null
    • 泛型只能放对象，不能放基本类型，比如 List<Long> 可以，List<long> 不行
    • 很多框架参数绑定、JSON 转换、MyBatis 映射都更常和包装类打交道

    基本类型不是对象，包装类是对象。

    包装类可以为 null，所以更适合数据库和框架。

    泛型里只能放包装类，不能放基本类型。

    2. 自动装箱和拆箱¶

    自动装箱：long -> Long 自动拆箱：Long -> long

    比如：

    1
2
    Long userId = 1L;     // 自动装箱
long id = userId;     // 自动拆箱

    这东西平时很方便，但有一个高频坑： 如果包装类是 null，拆箱时会空指针。

    比如：

    1
2
    Long userId = null; 
long id = userId; // NullPointerException

    这和你的项目很相关。比如统计代码里：

    1
    Integer totalOrderCount = orderMapper.countByMap(map);

    如果你后面直接拿它当基本类型算，而且没判空，就容易出问题。

    因此，应该需要“先判空再处理“。

    自动拆箱很方便，但 null 拆箱会空指针。

    3. String 是什么，为什么这么常用¶

    String 是不可变对象。 意思是：字符串一旦创建，内容不能改，所谓“修改”其实是新建了一个字符串。

    项目里最常见的字符串用途：

    • token
    • 订单号
    • 地址拼接
    • Redis key
    • 日志输出
    • 报表里的日期串

    6. 为什么要封装¶

    封装就是： 不让外部直接乱碰属性，而是通过方法来访问和修改。

    Java 里最常见的方式是：

    • 属性用 private
    • 提供 getter/setter

    比如：

    1
2
3
4

    return id;

    • 可以在设置值时做校验
    • 更符合面向对象设计

    7. 构造方法是什么¶

    最常见两种：

    无参构造

    一句话记忆： 框架喜欢无参构造，因为它们要先创建对象，再做属性填充。

    8. 什么是 JavaBean¶

    你项目里最常见的对象，其实大多都属于 JavaBean 风格。

    通常满足这些特点：

    • 有私有属性
    • 有无参构造
    • 有 getter/setter
    • 用来承载数据

    比如：

    • Employee
    • Orders
    • DishDTO
    • OrderVO

    为什么 JavaBean 在后端项目里这么常见？

    • 框架兼容性好
    • 适合做参数绑定
    • 适合做数据库映射
    • 适合做 JSON 序列化和反序列化

    所以你可以把 Entity/DTO/VO 理解成： 不同职责的 JavaBean。

    职责区别再复习一遍：

    • Entity：更贴近数据库表
    • DTO：接收前端参数
    • VO：返回给前端的数据

    如果一个类只有全参构造，没有无参构造，可能会对哪些框架场景造成不便？

    答：没有无参构造，会让很多依赖反射和属性填充的框架使用起来不顺手。比如：

    • MyBatis 查询结果封装对象
    • Jackson 反序列化请求体
    • BeanUtils、反射工具创建对象
    • 一些框架先实例化空对象再逐个填充属性的场景

    你项目里很多地方用了 BeanUtils.copyProperties，它为什么更适合在 Entity/DTO/VO 这种结构相近的对象之间使用？

    答：BeanUtils.copyProperties 适合在字段名和字段类型大体一致的 JavaBean 之间做快速拷贝，比如 DTO -> Entity、Entity -> VO。如果结构差异很大，或者需要复杂转换，它就不够合适了。

    10. Java 异常大体怎么分¶

    你现在先记最实用的一层：

    • Exception
    • RuntimeException

    面试和项目里最常用的区分就是：

    • checked exception 编译器强制你处理 比如某些 IO、反射、外部调用异常

    • unchecked exception 也就是运行时异常，继承 RuntimeException 编译器不强制你处理

    你项目里的业务异常，基本都属于第二类。比如：

    • OrderBusinessException
    • DeletionNotAllowedException
    • LoginFailedException

    这些异常本质是： 业务不满足条件，所以要中断流程并返回错误信息。

    • 业务异常：规则不满足，比如购物车为空、订单状态不对、超出配送范围
    • 系统异常：程序或环境出了问题，比如数据库连不上、空指针、网络调用崩了

    11. 为什么业务异常常继承运行时异常¶

    这是后端项目里很高频的设计。

    原因主要有 3 个：

    1. 业务校验失败本来就是运行阶段才知道的 比如“购物车是不是空”“订单状态对不对”，编译时不可能知道。
    2. 不想在每一层都写很多 throws 和 try-catch 如果业务异常都设计成受检异常，controller、service 一层层传会很重。
    3. 更适合和 Spring 事务、全局异常处理配合 抛出去后让统一异常处理器接住，代码更干净。

    你项目里这个设计就很典型：

    • service 里发现业务不满足条件
    • 直接 throw new xxxBusinessException(...)
    • 最后由全局异常处理器统一转换成前端能看懂的错误结果

    12. 你项目里的异常链路¶

    你可以直接看：

    • GlobalExceptionHandler.java
    • OrderServiceImpl.java
    • DishServiceImpl.java

    链路大概是这样：

    1. controller 收到请求
    2. service 做业务判断
    3. 如果条件不满足，抛业务异常
    4. GlobalExceptionHandler 统一捕获
    5. 返回统一格式的 Result.error(...)

    这套好处非常大：

    • controller 更干净
    • 错误处理风格统一
    • 前端更容易接
    • 业务语义更清晰

    13. 为什么不建议到处写 try-catch¶

    很多初学者喜欢这样写：

    // 业务逻辑

    问题是：

    • 错误信息被抹平了

    • 注解本质上是一种标记。

    • @AutoFill 是你项目里的自定义注解，用来标记公共字段自动填充。

    • 方法执行前做权限检查

    28. AOP 里最重要的 3 个概念¶

    1. 切点¶

    2. 通知¶

    在什么时候做增强

    你项目里用的是：

    意思就是： 在目标 mapper 方法执行前，先做自动填充。

    切点 + 通知 + 具体逻辑，合起来就是切面

    你项目里的：

    第一步：先标记¶

    在 mapper 方法上加：

    1

    或者：

    1

    意思是：

    • 这个方法执行时，需要自动填充
    • 而且要知道是插入还是更新

    第二步：切面找到它¶

    AutoFillAspect 通过切点表达式找到这些方法。

    也就是说，AOP 在做： “看到这个注解的方法，我就要插手一下。”

    第三步：方法执行前先增强¶

    @Before 通知会在 mapper 方法真正执行前先跑一遍。

    这里做的事情包括：

    • 读取注解
    • 取出操作类型
    • 取出实体对象
    • 通过反射设置公共字段

    第四步：目标方法再执行¶

    当字段补好了，真正的 mapper 插入/更新方法才继续执行。

    所以这整条链路就是：

    mapper 方法打标记 -> AOP 拦截 -> 自动填充字段 -> 执行 SQL

    30. AOP 和拦截器有什么区别¶

    这题很容易被追问，你现在先记一个够用版本：

    拦截器¶

    更偏 Web 层 主要拦 HTTP 请求

    比如你项目里的：

    • JwtTokenAdminInterceptor
    • JwtTokenUserInterceptor

    它们处理的是：

    • 请求有没有 token
    • token 合不合法
    • 当前用户是谁

    AOP¶

    更偏方法层 主要拦某些 Bean 的方法执行

    比如你项目里的：

    • AutoFillAspect

    它处理的是：

    • mapper 方法执行前，要不要补字段

    一句话区分： 拦截器拦请求，AOP 拦方法。

    “AutoFillAspect 是一个典型 AOP 场景。公共字段自动填充不是某个具体业务，而是多个模块都会用到的横切逻辑。项目通过 @Pointcut 找到 mapper 包下带 @AutoFill 的方法，再通过 @Before 在 SQL 执行前统一填充字段。拦截器主要拦 HTTP 请求，AOP 主要拦方法执行。”

    Spring 的事务管理是 AOP 吗？

    答：是的，Spring 的 @Transactional 可以理解为典型的 AOP 应用。它在业务方法执行前开启事务，方法正常结束后提交事务，如果出现符合回滚规则的异常就回滚。开发者只需要在方法上声明注解，事务的开启、提交、回滚由 Spring 通过代理和 AOP 机制完成。事务也是公共能力，适合通过 AOP 在方法前后统一增强。

    32. Stream 是什么¶

    Stream 不是集合本身，它是集合的一种处理方式。

    比如：

    1

    意思是： 把这个 List 变成一条可以连续处理的数据流。

    然后你可以接：

    • filter：筛选
    • collect：收集成集合
    • reduce：归约汇总

    注意： Stream 不会神奇地改变原集合，它通常是基于原集合生成一个新的结果。

    map 是转换¶

    map 的核心意思是： 把一种对象转换成另一种对象。

    你项目里最典型的是 OrderServiceImpl.java 的“再来一单”：

    你项目里在 ReportServiceImpl.java 有类似逻辑：

    这表示从 0 开始累加，不怕空列表。

    • GoodsSalesDTO -> numberList

    • 有很多分支判断
    • 需要频繁调试中间状态
    • 一写出来比 for 循环更难读

    ​所以别把 Stream 当成炫技，谁更清楚，就用谁。

    33. 什么是事务¶

    事务就是把多个数据库操作看成一个整体。

    比如用户下单不是一条 SQL：

    1. 插入订单主表
    2. 批量插入订单明细
    3. 清空购物车

    这三步必须整体成功。 如果订单主表插入成功，但明细插入失败，就会出现脏数据。 所以要用事务保证：

    要么三步都成功，要么一起回滚。

    事务有四个特性，叫 ACID。

    A：原子性¶

    一组操作要么都成功，要么都失败。

    比如下单三步不能只成功一半。

    C：一致性¶

    事务前后，数据要从一个正确状态变到另一个正确状态。

    比如不能出现“有订单但没有订单明细”的异常状态。

    I：隔离性¶

    多个事务并发执行时，彼此不能随便互相干扰。

    比如两个人同时操作订单，不能把状态改乱。

    D：持久性¶

    事务提交后，数据要真正保存下来。

    比如订单提交成功后，数据库里应该能查到。

    你现在先不用背复杂理论，先能结合项目举例就够了。

    • DishServiceImpl.java 的新增、删除
    • SetmealServiceImpl.java 的新增、删除、修改

    35. @Transactional 做了什么¶

    @Transactional 是 Spring 声明式事务注解。

    你加在 service 方法上后，Spring 会在方法执行时帮你做：

    1. 方法开始前开启事务
    2. 方法正常执行完提交事务
    3. 方法执行中出现符合规则的异常就回滚事务

    这背后也是 AOP 思想： 在业务方法前后加事务控制。

    36. 什么异常会触发回滚¶

    默认情况下，Spring 对运行时异常 RuntimeException 和 Error 回滚。

    你项目里的业务异常很多继承运行时异常，所以抛出后可以触发回滚。

    比如：

    • ShoppingCartBusinessException
    • OrderBusinessException
    • DeletionNotAllowedException

    注意： 如果是受检异常 Exception，默认不一定回滚，除非配置：

    1
    @Transactional(rollbackFor = Exception.class)

    你项目里有些方法声明了 throws Exception，但是否回滚要看异常类型和事务配置。这个作为进阶点先记住。

    事务失效的常见情况¶

    4 个高频点。

    1. 方法不是 Spring Bean 调用的：如果对象是自己 new 出来的，不归 Spring 管，事务不生效。

    2. 同类内部方法调用：比如同一个类里 methodA() 调 methodB()，而事务只加在 methodB() 上，可能绕过 Spring 代理，导致事务不生效。

    3. 异常被 catch 了没抛出去：如果异常被你自己吃掉，Spring 以为方法正常结束，就会提交。

    4. 默认只回滚运行时异常：受检异常默认不一定回滚，需要 rollbackFor = Exception.class。

    37. 为什么事务通常放在 service 层¶

    因为 service 层负责完整业务编排。

    比如下单：

    • 校验地址簿
    • 查购物车
    • 插订单
    • 插明细
    • 清购物车
    • 返回结果

    mapper 只知道单个数据库操作，不知道完整业务。 controller 又不应该负责业务细节。

    39. 动态 SQL 是什么¶

    46. 为什么普通 HashMap 有并发风险¶

    普通 HashMap 不是线程安全的。

    如果多个线程同时：

    • put
    • remove
    • 遍历
    • 发送消息时读取

    可能出现：

    • 数据覆盖
    • 数据不一致
    • 遍历时被修改导致异常
    • 某些连接丢失或状态错乱

    在 WebSocket 场景下，多个客户端可能同时建立连接、断开连接、接收消息。 这些事件不一定只由一个线程串行处理。

    所以 HashMap 并发访问是不稳的。

    47. ConcurrentHashMap 是什么¶

    ConcurrentHashMap 是 Java 提供的并发安全 Map。

    它适合多个线程同时读写。 相比直接给整个 Map 加大锁，它通常并发性能更好。

    你的项目里可以把：

    1
    private static Map<String, Session> sessionMap = new HashMap<>();

    优化为：

    1
    private static final Map<String, Session> sessionMap = new ConcurrentHashMap<>();

    这就是一个很自然的项目优化点。

    面试里可以这样说：

    “当前教学项目中 WebSocket 会话使用普通 HashMap 保存，功能测试没问题。但真实并发环境下多个连接可能同时 put/remove/send，普通 HashMap 不是线程安全的，可以改成 ConcurrentHashMap。”

    48. Spring Bean 默认是单例，也要注意成员变量¶

    这是很多人容易忽略的点。

    Spring 里的 @Service、@Controller 默认是单例。 也就是说，同一个 Bean 对象会被多个请求线程共享。

    所以在单例 Bean 里，不要随便放“会被请求修改的成员变量”。

    比如这样就危险：

    1
2
3
    @Service public class OrderServiceImpl {
    private Long currentUserId;
}

    如果多个请求同时改这个字段，用户 id 就可能串。

    你项目里用 ThreadLocal 保存当前用户 id，而不是把它放到 service 成员变量里，这就是正确方向。

    50. 垃圾回收 GC 是什么¶

    Java 不需要你手动 free/delete 对象。 JVM 会自动回收不再使用的对象。

    所谓“不再使用”，最常见理解是：

    没有任何可达引用指向它。

    比如一个请求里创建了很多：

    • Orders
    • OrderVO
    • List<OrderDetail>
    • HashMap

    请求结束后，如果这些对象没有被其他地方引用，它们就可以被 GC 回收。

    51. 为什么还要关心对象数量¶

    虽然 Java 有 GC，但不代表可以随便创建对象。

    如果短时间创建大量对象：

    • 堆内存压力变大
    • GC 更频繁
    • 接口响应可能抖动
    • 极端情况会 OOM

    比如报表导出、批量查询、大量集合转换，都可能创建很多对象。

    你项目里的 POI 导出 Excel 就是一个需要注意内存的场景。 真实大数据量导出时，不能无脑一次性把所有数据都堆在内存里。

    56. 支付和订单幂等¶

    幂等的意思是：

    同一个操作执行多次，结果应该和执行一次一样。

    支付回调尤其需要幂等。 因为支付平台可能重复通知。

    如果同一个支付成功通知来了两次，系统不能：

    • 重复改状态导致异常
    • 重复推送多次来单消息
    • 重复发放优惠
    • 重复创建数据

    所以真实支付回调一般会：

    • 根据订单号查订单
    • 判断当前支付状态
    • 如果已经支付过，直接返回成功
    • 没支付过才更新状态

    你项目里支付逻辑偏教学实现，后续可以把“支付幂等”作为优化点。
